# Native policy usage

The adjacent JSON is a template, not a submitted configuration. Replace its symbolic participant with the actual authorized non-author agent UUID. Read back the saved policy. This repository does not implement a workflow engine.

Configure and read back required source-task stages through the supported issue PATCH before submission. Publish and independently retrieve the immutable candidate before releasing its separate R/V examinations or adding their real blockers. R/V report completion can carry FAIL. After both finish, the producer saves and reads back exact candidate references, report revisions, findings, limitations and the continuation packet, then submits the unchanged candidate to in_review as the final required action of that run.

At every wake, read the current task, persisted evidence and executionState.currentParticipant, currentStageType and returnAssignee. The incoming participant verifies the exact candidate and original producer return identity, and records this verification in its own continuing context. Only the active native participant may decide: status done approves; status in_progress with a reason requests changes. Include rationale in that same operation, after saving/reading back findings and continuation. Native changes-requested returns the original producer; do not manually reassign to simulate it. A transition may end the outgoing run immediately. The incoming participant reads and records the actual decision ID/outcome and resulting assignment; no mandatory outgoing command, comment or receipt follows the transition.

For framework/application artifacts, Assurance is the non-author participant. For Assurance-authored TS use the Delivery Lead; for TC use the Product Engineer. A required human business approval is a separate user participant with an actual authorized user ID. Do not add a stage that makes an author approve their own output.

Coordination tasks initially waiting for human/operator input have a saved interaction and no deliverable stage. When the readiness evidence arrives, resume production, attach/read back the approved stage, obtain separate R/V evidence and only then submit the deliverable. Setting in_review to wait for input must not prematurely start deliverable acceptance.

A new candidate requires fresh affected evidence even if native resubmission resumes the failed stage. Preserve earlier report revisions and unresolved acceptance blockers when replacing blockedByIssueIds. Do not create source-done dependencies for its R/V tasks. Cancellations are not successful blocker resolution. If an acceptance-blocked coordinator cannot run authorized production, use the separately authorized production assignment with only its actual production prerequisites; retain the coordinator's acceptance edges and original return identity.

Use unresolved issue dependencies for issue waits, saved pending interactions/approvals for decisions, and concrete actions with permitted owners for technical blockers. Do not repeatedly mark work blocked against already-completed dependencies. A comment promising later work is not a scheduled continuation. CEO recovery coordination stays on the existing coordinator: inspect the native notice, reconcile request/result evidence and live state, record a concrete disposition, and dispatch a supported native action within existing authority. Otherwise surface the exact decision still needed and its responsible actor. Correct the actual startup failure before requesting a retry.

For an explicitly authorized platform test, separate the target's ownership lifecycle from the test actor's execution assignment. Establish access/route preconditions without spending a decision attempt. Snapshot stable target review, active participant, original return identity and concurrency arrangements; reviewer checkout or ordinary metadata PATCH can change native state. Do not presume these writes are state-neutral. Record actor/run, exact non-secret request/response and before/after state durably on the execution assignment before it hands off. A wrong-actor check passes only with participant-specific rejection and unchanged state; unrelated errors or concurrent changes are inconclusive. Missing evidence remains UNKNOWN and neither a stopped run nor a revised plan renews authorization. See [continuation](../continuation.md) for interrupted-operation reconciliation. These are operating rules, not extra platform permissions, an orchestrator or automatic merge/deployment.
