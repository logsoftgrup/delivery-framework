# Harness qualification expectations — TS-2

This specifies good and bad fixtures for later independently reviewed TEST.TC code. No harness or app implementation is authored or executed here. Qualify the runner against synthetic controlled fixtures before trusting app results. Fixtures are isolated offline responses/pages/config records or named QA resources; never damage a real deployment to manufacture a failure. Record each fixture's immutable SHA, intended defect, scenario exercised, suite SHA, request/evidence and observed verdict. A good harness rejects an invalid result as an ordinary assertion FAIL; runtime/environment failures are separately UNAVAILABLE/UNKNOWN, never PASS.

| ID | Good fixture and expected harness result | Bad fixture and expected harness result |
|---|---|---|
| HAR-01 exact contract | 201 correct trimmed Item, unchanged old tuples + one distinct ID; exact errors with unchanged tuples: relevant API cases PASS | 200 in place of 201; wrapped/missing/extra keys; incorrect error code/message/fields: relevant assertions FAIL, even if content seems useful |
| HAR-02 C0 sentinel | Whitespace POST returns exact 422 E-LENGTH and no tuple: API-05 PASS | 201 empty name/insert, or 422 but inserts anyway: API-05 FAIL. Runner exits unsuccessfully for required failure; neither xfail nor expected-failure credit counts as application PASS |
| HAR-03 Unicode | Literal API fixtures preserve the full scalar oracle. Browser fixture establishes its explicit control value, records entry method and tests the separate browser oracle. API-created newline display also checked: mapped checks PASS | JS-unit/grapheme count error, broad trim, normalization, treating removed LF/CR as proven app trimming, deriving expected strings from observed values, or omitting API newline/display checks: corresponding assertion/qualification FAIL. Failed fixture setup cannot become a candidate PASS |
| HAR-04 ordering/identity | F-ORDER exact ordering and tuples, duplicate names with different IDs: DATA-01/02/API-14 PASS | Equal-time rows reversed, repeated ID, replaced old tuple with same count, invalid UTC/v4, missing row: FAIL. Proves snapshots are not count-only |
| HAR-05 uncertainty | 500/dropped-response pre/postcommit variants reconcile by GET, retain input, no second POST: UI-07–09 PASS | Automatic POST retry, definite-failure copy on 500, name-match success inference, reenable Create after failed GET or repeat create after 201 refresh failure: FAIL |
| HAR-06 browser/AX | Correct label/error/status/focus; text nodes; no clipping at both required viewports: automated subset PASS, manual subset still PENDING | InnerHTML markup, missing label/error association, focus hidden, duplicated create, clipped error or low contrast: appropriate browser/manual checks FAIL. A clean scanner cannot make keyboard/AT cases PASS |
| HAR-07 record durability | Same acknowledged IDs/names/times across process and container restart, initialized empty remains empty: DATA cases PASS | Recreated seeds, regenerated IDs, one lost acknowledged item, GET inserts probe: FAIL |
| HAR-08 target safety | Explicit QA URL, expected task/project/environment/resource name+labels/IDs/config and validated route: proceed with authorized fixture operation | Review/default/unknown URL; matching name wrong label; QA points at review volume or shares network: stop before any request that could write/reset. UNAVAILABLE safety gate; prove zero mutation. Never run negative safety fixture against actual review |
| HAR-09 identity | Exact app/scenario/suite SHA, image manifest/config/archive hash and version/config all agree: eligible for execution | Mutable tag only, different image same version text, archive corruption, stale suite/hash: refuse result attribution, UNAVAILABLE identity gate, no PASS |
| HAR-10 runner integrity | Every required parameter/SC/manual obligation accounted; durable raw evidence + explicit results, failures propagate to process/summary: summary accurate | Swallowed assertions, zero collected tests, omitted whitespace variant, disabled/xfail cases, wrong base URL, stale report from another run, missing artifact, a crash/timeout or access-denial converted to PASS: qualification FAIL; interrupted current app outcome UNKNOWN |
| HAR-11 recovery | Recorded C1 target with qualifying independent subset and verified restore point; backup tuples/config/artifact match: OPS eligibility met | C0 target, unrelated digest, checksum mismatch, incompatible schema or no qualifying evidence: stop recovery before switch, leave originals intact; OPS qualification FAIL/UNAVAILABLE as observed. No requirement for completed O2 to start O2 |
| HAR-12 manual/evidence separation | Automation summary links pending/completed real manual/H records and names limits; native history unchanged: accurate limited report | Fake screen-reader transcript, agent-authored human verdict, producer run relabelled independent, unknown session reset claimed fresh or self-authored suite acceptance: evidence FAIL, relevant gate stays open |

Run each intentionally bad variant separately with an otherwise good fixture so failure attribution is clear; do not count unrelated crashes as detection. Restore good fixture afterwards to check the intended failure is localized. Never change expected outcomes to turn C0 green. A harness qualification PASS is about detecting these controlled fixtures; application C0 still FAILs. If the runner cannot distinguish setup failure from assertion failure, TC needs correction by its original author and new non-author examination.

TC handoff must include reset/fault mechanism source paths, no-review guard, fixture identities, runner exit/report semantics, exact dependency/tool versions, all parameter-to-test mappings and evidence location. Synthetic response fixtures cannot prove real DB durability, actual browser accessibility, host access or operator recovery; corresponding real V evidence remains mandatory.
