## Journey and boundaries

In the existing authenticated host remote desktop, a human opens the verified review URL, sees “Synthetic data only”, creates “Pilot notebook”, sees exactly one additional item and finds that same ID after reload. Invalid input explains the correction without inserting anything. A simulated API failure preserves input and supports the recovery described in [UI reference](ui-reference.md).

One page, one create form, one item list. List and create only. No edit/delete/search, application accounts, payment, notification, business integration, production hosting, SLA/load certification or real data. Infrastructure authentication is external to the application. No framework redesign, platform capability retest, automatic merge/deployment, new agent or access expansion. Formal test design and test-code authoring belong to the separate TS and TC assignments; this document defines expectations, not an acceptance test implementation.

## Lifecycle and evidence

1. Publish BASE-2 on authorized `smoke/phase-b`; retrieve its full SHA and complete file set through a separate remote fetch. `baseline-manifest.json` hashes files; its own identity is its Git blob plus the enclosing commit, avoiding self-reference. Source packet records all identities.
2. Save/read back precise inputs to existing BASE.R (LOGA-25) and BASE.V (LOGA-26), retaining Assurance `ce8e0a2f-a532-45cb-abeb-a3937e9be71e`. Release ready examinations and attach real native blockers to this source. They do not depend on source completion. Neither task may repair this candidate.
3. Completed static examinations may carry FAIL. Keep the unchanged candidate, exact report revisions, findings and limitations. Save/read back continuation, then submit source for configured Assurance review followed by native human baseline approval. Submission is the final required operation in that run. No self-acceptance.
4. On changes-requested, verify exact failed SHA and native returnAssignee equals the original producer before correction. Publish a new SHA and refresh affected examinations on the same tasks; preserve old reports. Never repair during examination/review.
5. Approved baseline permits only the separately released downstream assignments. TS/TC and app runtime inputs must be ready before runtime examination. C0's single intentional whitespace-only API defect is confined to isolated QA, visibly identified in evidence; it is not a waiver of B2 and cannot be promoted to human review.

Every report includes criterion/verdict, expected/actual, file/line or request/response evidence, actor/run, source and suite/scenario identities, image/config/fixture/route identities when relevant, limitations and next permitted owner/action. Static work records runtime/suite/image as N/A, with the reason. Continuation follows the pinned F2 template: current task/stage/participant/original return, candidate/report revisions, unresolved dependencies/interactions, interrupted-operation evidence and next action. Record prepared/dispatch-started/response-confirmed/evidence-saved separately; UNKNOWN is not proof of non-execution or permission to replay. Read live native state before any recovery mutation.

## Release gates retained by this baseline

Static acceptance can proceed while [architecture selections](architecture.md#build-inputs-and-open-selections) and [operational gaps](runbook.md#observed-facts-and-open-gates) remain explicit. Application build/package readiness needs resolved direct/transitive versions, verified base digest and platform, tool identities and compatible lock. Runtime/human release also needs authorized CI publication/capacity, known-good recovery evidence, independent passing C1, actual host port/route/storage checks and native approvals. A documentation PASS closes none of these runtime gates.
